# 监督、恢复、合并与主工作树复验

## 长任务监督

长任务至少需要一个与运行时无关的监督契约：

- 记录当前 task-id、进程或运行句柄、worktree、branch、checkpoint 和日志；
- 使用真实业务活动判断冻结，不把 stdout 重定向文件的 mtime 当成唯一心跳；
- 健康状态保持安静，冻结或完成只通知一次；
- 监督器退出或报告完成只表示生命周期变化，不表示验收通过；
- 主代理、运行时或机器重启后，能够从持久状态恢复，而不是重新猜测目标。

监督器发现冻结时，只终止自己明确绑定的当前任务进程，绝不按进程名称杀掉其他项目的运行。

## 冻结或失败恢复

1. 保存当前日志、Git 状态、测试产物和报告。
2. 读取最新业务活动和当前子进程，区分真正冻结、等待测试、权限阻塞和正常退出。
3. 保留现有 worktree、branch、未提交实现和任务级证据。
4. 必要时创建明确的 checkpoint，不要为了“干净”删除现场。
5. 如果契约需要改变，先记录裁决，再创建 continuation 任务单和新的证据目录。
6. 重新派发前使用新的运行日志和监督绑定，核对 checkpoint 与实际 branch。

退出码为零、通知到达或测试数量增加都不能绕过这一步。

## 合并前

合并输入必须是 `git worktree list` 中确认过的 branch ref，而不是仅凭旧路径。主代理检查：

- worktree 状态和冲突索引；
- `git diff --check`；
- 当前任务的三份报告和每条验收测试的证据；
- 任务单验收台账与执行记录；
- 改动路径和范围；
- 分支是否包含任务单冻结提交；
- 是否有其他运行正在操作同一 worktree 或主分支。

先提交实现，再单独提交当前任务的证据和状态文件；不要使用会吸收无关产物的全量暂存命令。

## 合并后

主工作树可能没有 worktree 中的依赖、原生模块或构建产物。合并后按项目真实命令执行：

1. 检查依赖和生成物是否可加载；
2. 若任务修改 manifest 或 lockfile，先用项目批准的冻结安装重新水合主工作树；
3. 重新运行聚焦验收测试、全量测试、构建、post-build 测试、lint 和差异检查；
4. 检查合并提交的文件路径，确认没有把监督标记、临时文件或其他任务内容带入；
5. 验证主分支状态和远程状态，再标记已合并。

worktree 通过而主工作树失败时，任务仍是 FAIL/BLOCKED，不能因为合并已经发生就改成完成。

## 状态恢复与并发护栏

每次后台间隙、会话切换或电脑重启后，在写报告、提交、合并或派发前重新核对：

- 持久任务状态；
- 主分支 HEAD；
- `git worktree list`；
- 当前任务单；
- 活动进程和最新日志；
- 是否已有另一个主代理接管并完成任务。

如果任务已完成或 worktree 已被重新绑定，旧上下文必须停止，不能覆盖新证据。
