# 验收矩阵与证据完整性

## AC 必须可执行

每条验收标准都必须绑定：

- 精确测试文件和用例名；
- 触发动作和输入；
- 具体断言，包含成功、失败、持久化和恢复边界；
- 完整命令、工作目录、环境前置和超时；
- 当前轮次的实际输出、退出码和产物路径。

“跑全量测试”“功能正常”“所有 AC 通过”都不是验收证据。

## 验收台账

每条 AC 保持一行：

| 字段 | 要求 |
|---|---|
| AC | 与当前任务单完全一致 |
| 测试 | 当前文件和精确用例名 |
| 行为 | 证明的产品不变量 |
| 命令 | 实际运行的完整命令 |
| 结果 | 当前输出、退出码和超时边界 |
| 复验 | 审查子代理直接运行或检查的结果 |
| 证据 | 当前任务的报告或原始输出路径 |

缺少任何一项，不得标记 PASS。

## 矩阵而不是测试数量

测试数量增长、全量命令为绿色或报告声称“完整矩阵”都不能证明覆盖完整。审查时直接读取高风险测试正文，确认：

- 表格参数真正影响 fixture、输入或故障点；
- 每个变体都有不同的断言；
- 期望值不是从被测路径重新计算出来的；
- 不存在 `undefined === undefined`、空数组往返、自比较或永远为真的断言；
- 多进程、重启、回滚、互斥和隔离要求使用真实边界，而不是同进程 Promise 并发或手写终态。

## 证据身份和新鲜度

每份报告必须标明：task-id、worktree、branch、角色、轮次、生成时间、当前测试数量和关键命令。当前任务的报告目录必须与任务单完全同名。

以下情况都使报告失效：

- 报告引用其他任务、其他 worktree 或旧 branch；
- worktree 在报告后继续变化而报告没有重生成；
- reviewer 只复制执行报告；
- 报告只有结论，没有命令和断言；
- 任务单的 AC 或范围已经改变，但报告没有对应 continuation。

## 证据等级

不同证据只能证明不同边界：

1. 领域/算法单元测试；
2. 协议、核心服务和持久化集成测试；
3. 组件或前端测试；
4. 真实浏览器、桌面或移动端用户路径；
5. 多进程、真实网络或真实设备端到端测试。

任务单必须声明每条 AC 需要哪个等级。低等级通过不能替代高等级验收。

## 时间限制

默认每条测试或单条测试命令设置三分钟硬上限，超时立即停止并诊断。整套测试可能包含多个文件和编译阶段，应使用更大的、明确的累计上限，不能把每条测试的三分钟机械地当成全套测试的三分钟。

网络操作、子进程、数据库锁和后台 worker 的双方都要有有界等待；失败后必须收集现场并退出，不能留下无限等待的进程。

## 结论分类

使用明确状态：`PASS`、`FAIL`、`BLOCKED`、`FLAKY`、`EXPLORATORY_ONLY`。

重试后通过是 `FLAKY`，不是干净的 `PASS`；测试环境缺少真实 API 是 `BLOCKED`，不是把断言降级后的 `PASS`。
